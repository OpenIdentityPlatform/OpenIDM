[#chap-ldap]
== Generic LDAP Connector

The generic LDAP connector uses JNDI to manage entries in LDAPv3 directories, including OpenDJ, OpenLDAP, and Microsoft Active Directory.

Use the bundled Java connector for Active Directory Domain Services or Active Directory Lightweight Directory Services (AD LDS). It can run in the OpenIDM JVM. For integrations that require Windows or PowerShell APIs, see xref:chap-powershell.adoc#chap-powershell[PowerShell Connector Toolkit].

[#ldap-connector-config]
=== Setting Up the Generic LDAP Connector

OpenIDM ships `connectors/ldap-connector-<version>.jar`. Copy a template from `samples/provisioners/` to the active project's `conf/` directory and adapt it to your directory.

* `provisioner.openicf-opendjldap.json` is an OpenDJ template.
* `provisioner.openicf-ldap.json` and `provisioner.openicf-ldap2.json` are generic LDAP examples.
* `provisioner.openicf-adldap.json` is an Active Directory Domain Services template.
* `provisioner.openicf-adldsldap.json` is an Active Directory Lightweight Directory Services template.

The following example configures a local connector with an LDAPS connection to an OpenDJ server. Replace the host, port, bind identity, and base DNs with values from your directory. Provide the bind password using xref:../integrators-guide/chap-configuration.adoc#using-property-substitution[property substitution] or update it through the Admin UI.

[source,json]
----
{
  "connectorRef": {
    "bundleName": "org.openidentityplatform.openicf.connectors.ldap-connector",
    "bundleVersion": "[2.0.0.0,3)",
    "connectorName": "org.identityconnectors.ldap.LdapConnector"
  },
  "configurationProperties": {
    "host": "ldap.example.com",
    "port": 1636,
    "ssl": true,
    "principal": "uid=openidm,ou=services,dc=example,dc=com",
    "credentials": "&{ldap.bind.password}",
    "baseContexts": ["dc=example,dc=com"],
    "baseContextsToSynchronize": ["dc=example,dc=com"],
    "accountUserNameAttributes": ["uid"],
    "uidAttribute": "entryUUID"
  }
}
----

For StartTLS, set `ssl` to `false`, set `startTLS` to `true`, and use the regular LDAP port. Configure trust for LDAPS or StartTLS in the Java process running the connector. Import the directory's issuing CA into the truststore used by that JVM and specify its absolute path with `-Djavax.net.ssl.trustStore` if using a custom truststore. Use the DNS name from the server certificate as the host. For a remote connector, set `connectorHostRef` in `connectorRef` and configure trust in the connector server JVM.

Choose a stable `uidAttribute`, such as OpenDJ's `entryUUID` or Active Directory's `objectGUID`. Some sample configurations use `dn`, which changes on rename or move. Changing the UID representation of an existing provisioner also changes external identifiers already stored in OpenIDM links.

Use a bind identity with access to the configured bases and attributes. Grant write or changelog access only for the operations you plan to use. Test the connection, then check the generated object schema and query the configured resources. See xref:../integrators-guide/chap-resource-conf.adoc#systems-over-rest[Using Connectors Over REST] and xref:#sec-config-properties-org-identityconnectors-ldap-LdapConnector-1_4_1_2[LDAP Connector Configuration].


[#ldap-connector-sync-controls]
=== Controlling What the LDAP Connector Synchronizes

`baseContexts` and the `accountSearchFilter` and `groupSearchFilter` properties control LDAP searches, including searches during reconciliation. Configure `baseContexts` to cover both accounts and groups that the provisioner must manage. Set the account and group search filters to include the entries you want OpenIDM to see.

For LiveSync, set `baseContextsToSynchronize` explicitly. The `cn=changelog` strategy falls back to `baseContexts` when this list is empty. The Active Directory and timestamp strategies search the configured synchronization bases directly. Use `accountSynchronizationFilter` or `groupSynchronizationFilter` for the matching LiveSync object class. The `cn=changelog` strategy also looks up changed entries through the connector's search logic. These properties act on LDAP data, while outbound implicit synchronization is controlled by the OpenIDM mapping.

The connector selects a sync strategy based on the detected directory type. It uses the `cn=changelog` strategy for OpenDJ and compatible directories, the IBM change log for IBM Directory Server, and `uSNChanged` for Active Directory Domain Services and AD LDS. OpenLDAP, Active Directory Global Catalog, and unrecognized directory types default to timestamp searches. Set `useTimestampsForSync` to `true` to force the timestamp strategy. It polls creation and modification timestamps and cannot detect deletes. If you switch strategies, reconcile and reinitialize the LiveSync state since token formats differ.

For USN LiveSync against AD DS, set the configured `port` to `389` for LDAP or `636` for LDAPS. The connector classifies an AD DS endpoint on any other configured port as a Global Catalog and uses timestamp searches. This also applies to a domain controller reached through a forwarded port such as `1636`.

For account and group USN LiveSync against Active Directory, use a consistent domain controller because the update sequence numbers belong to that server. Detecting deletions requires access to the Deleted Objects container and support for the Show Deleted control. For AD LDS, the server must also expose a default naming context.

For non-delete events in the `cn=changelog` strategy, `objectClassesToSynchronize` limits which changed entries are returned, and `attributesToSynchronize` limits which changed attributes trigger an event. When `synchronizePasswords` is enabled, the connector adds `passwordAttributeToSynchronize` to the filter. An empty `attributesToSynchronize` list then matches only changes that include that change log attribute. With `synchronizePasswords` disabled, an empty list disables filtering by attribute. Entry deletions bypass the attribute filter.

The timestamp and Active Directory strategies use `objectClassesToSynchronize` for an all-object-classes request and derive the class filter from the account or group mapping for class-specific requests.

For directories that record modifier DNs in their change logs, use a dedicated OpenIDM bind DN and add it to `modifiersNamesToFilterOut` to avoid replaying OpenIDM's own writes back into managed objects. The `cn=changelog` strategy checks `modifiersName` and, for deletes, `changeInitiatorsName`. Active Directory's USN and the timestamp strategies do not use this option.

For more on reconciliation, LiveSync, and implicit synchronization, see xref:../integrators-guide/chap-synchronization.adoc#sync-types[Types of Synchronization].


[#ldap-connector-with-ad]
=== Using the Generic LDAP Connector With Active Directory

Start with `samples/provisioners/provisioner.openicf-adldap.json` for Active Directory Domain Services. Set `host`, `principal`, `credentials`, `baseContexts`, and `baseContextsToSynchronize` for your environment. The template maps `objectGUID` to the connector UID, `sAMAccountName` to the authentication lookup attribute, and `member` to the group membership attribute. The sample account filters exclude disabled users and computers. Adapt both account filters if you need to manage or synchronize disabled users. For USN LiveSync, follow the port and domain controller requirements in xref:#ldap-connector-sync-controls[Controlling What the LDAP Connector Synchronizes].

The connector exposes these native attributes for managing Active Directory accounts. Map them in `objectTypes.account.properties` using the expected type and the native name used by the connector. The sample already maps `isActive` to `+__ENABLE__+`.

* `+__ENABLE__+` reads or writes the disabled flag in `userAccountControl`.
* `+__ACCOUNT_EXPIRES__+` writes the `accountExpires` LDAP attribute from a UTC timestamp or the special value `0` for no expiration. The LDAP attribute `accountExpires` is available on reads.
* `+__LOCK_OUT__+` reports lockout status using `msDS-User-Account-Control-Computed` where available. To unlock a user, set it to `false`, which writes `lockoutTime=0`. Setting it to `true` has no effect.
* `+__PASSWORD_EXPIRED__+` reports password expiration from the directory and writes `pwdLastSet` on changes. Set it to `true` to write `0` and require a password change at next logon, or to `false` to write `-1` and clear that requirement.
* `+__DONT_EXPIRE_PASSWORD__+`, `+__PASSWORD_NOTREQD__+`, and `+__SMARTCARD_REQUIRED__+` expose the corresponding `userAccountControl` flags when available.

For an end-to-end setup, see xref:../how-to/active-directory-identity-management.adoc#active-directory-identity-management-active-directory-connector-configuration[Active Directory Connector Configuration].


[#ldap-connector-ad-users]
==== Managing Active Directory Users With the LDAP Connector

Use LDAPS for account provisioning with passwords. For this example, connect to a writable AD DS domain controller and set `ssl` to `true` and `port` to `636` in the provisioner. The connector translates `+__ENABLE__+` to `userAccountControl` on create only when it classifies the server as `MSAD`, using the configured port. Configure the JVM truststore as described in xref:#ldap-connector-config[Setting Up the Generic LDAP Connector].

The AD template sets `passwordAttribute` to `unicodePwd` and `passwordHashAlgorithm` to `WIN-AD` so the connector encodes the password for Active Directory. Add `password` to `objectTypes.account.properties` if it is absent from the provisioner.

[source,json]
----
{
  "password": {
    "type": "string",
    "nativeName": "__PASSWORD__",
    "nativeType": "JAVA_TYPE_GUARDEDSTRING",
    "flags": ["NOT_READABLE", "NOT_RETURNED_BY_DEFAULT"]
  }
}
----

To create an enabled account, first remove `NOT_CREATABLE` from the `objectTypes.account.properties.isActive.flags` array in your copy of the provisioner. Then send the following request. Substitute test credentials and adapt the DN, account name, and URL to your environment. The sample requires `sn`. Active Directory derives `cn` from the RDN in `dn`.

[source,bash]
----
curl --fail-with-body \
  --header "Content-Type: application/json" \
  --header "X-OpenIDM-Username: $IDM_USER" \
  --header "X-OpenIDM-Password: $IDM_PASSWORD" \
  --request POST \
  --data '{
    "dn": "CN=Brian Smith,CN=Users,DC=example,DC=com",
    "sn": "Smith",
    "givenName": "Brian",
    "sAMAccountName": "bsmith",
    "userPrincipalName": "bsmith@example.com",
    "isActive": true,
    "password": "replace-with-a-test-password"
  }' \
  'http://localhost:8080/openidm/system/ad/account?_action=create'
----

The returned `_id` is the encoded Active Directory GUID. Verify in Active Directory that the account is enabled. For `userAccountControl` flag values, see link:https://learn.microsoft.com/en-us/troubleshoot/windows-server/active-directory/useraccountcontrol-manipulate-account-properties[Microsoft's reference].


[#ldap-connector-ad-groups]
==== Managing Active Directory Groups With the LDAP Connector

The connector maps `+__GROUP_SCOPE__+` and `+__GROUP_TYPE__+` to Active Directory's `groupType`. The scope values are `global`, `domain` (domain local), and `universal`. The type values are `security` and `distribution`. If omitted when creating a group, the defaults are `global` and `security`. See link:https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-groups[Active Directory security groups].

To specify scope or type through the sample provisioner, add the following mappings to `objectTypes.group.properties`.

[source,json]
----
{
  "scope": {
    "type": "string",
    "nativeName": "__GROUP_SCOPE__",
    "nativeType": "string"
  },
  "groupKind": {
    "type": "string",
    "nativeName": "__GROUP_TYPE__",
    "nativeType": "string"
  }
}
----

Send a `POST` request to `/openidm/system/ad/group?_action=create` with the following body to create a universal distribution group. Sending only `dn` uses the default group scope and type.

[source,json]
----
{
  "dn": "CN=Employees,CN=Users,DC=example,DC=com",
  "scope": "universal",
  "groupKind": "distribution"
}
----


[#ad-dates]
==== Handling Active Directory Dates

Active Directory represents `pwdLastSet`, `accountExpires`, `lockoutTime`, and `lastLogon` in 100-nanosecond intervals since January 1, 1601 UTC. The connector reads these fields as UTC strings in `yyyy-MM-dd'T'HH:mm:ss'Z'` format, for example `2015-03-02T20:17:48Z`. It preserves the sentinel string `0` and returns `0` for the `accountExpires` no-expiration value `9223372036854775807`. Fields such as `whenCreated` and `whenChanged` are LDAP generalized time and retain their directory format.


[#sec-implemented-interfaces-org-identityconnectors-ldap-LdapConnector-1_4_1_2]
=== OpenICF Interfaces Implemented by the LDAP Connector

The LDAP Connector implements the following OpenICF interfaces.
--

xref:appendix-interfaces.adoc#interface-AuthenticationApiOp[Authenticate]::
Finds the account using `accountUserNameAttributes` and attempts an LDAP bind with the supplied password.

xref:appendix-interfaces.adoc#interface-CreateApiOp[Create]::
Creates an object and its `uid`.

xref:appendix-interfaces.adoc#interface-DeleteApiOp[Delete]::
Deletes an object, referenced by its `uid`.

xref:appendix-interfaces.adoc#interface-ResolveUsernameApiOp[Resolve Username]::
Resolves an object by its username and returns the `uid` of the object.

xref:appendix-interfaces.adoc#interface-SchemaApiOp[Schema]::
Describes the object types, operations, and options that the connector supports.

xref:appendix-interfaces.adoc#interface-ScriptOnConnectorApiOp[Script on Connector]::
Enables an application to run a script in the context of the connector. Any script that runs on the connector has the following characteristics:
+

* The script runs in the same execution environment as the connector and has access to all the classes to which the connector has access.

* The script has access to a `connector` variable that is equivalent to an initialized instance of the connector. At a minimum, the script can access the connector configuration.

* The script has access to any script-arguments passed in by the application.


xref:appendix-interfaces.adoc#interface-SearchApiOp[Search]::
Searches the target resource for all objects that match the specified object class and filter.

xref:appendix-interfaces.adoc#interface-SyncApiOp[Sync]::
Polls for changes using the configured directory synchronization strategy.

xref:appendix-interfaces.adoc#interface-TestApiOp[Test]::
Validates the configuration, binds to the directory, and checks the configured base DNs.

xref:appendix-interfaces.adoc#interface-UpdateApiOp[Update]::
Updates (modifies or replaces) objects on a target resource.

--
