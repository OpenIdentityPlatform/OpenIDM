[#chap-ad]
== Active Directory Connector

The legacy Active Directory connector uses Windows Active Directory Service Interfaces (ADSI) to provision and synchronize Active Directory Domain Services accounts, groups, and organizational units. The OpenIDM distribution supplies a sample provisioner. Install the connector DLL separately on a Windows .NET Connector Server from link:https://github.com/OpenIdentityPlatform/OpenICF.Net/releases/download/1.5.0/ActiveDirectory.Connector-1.5.0.0.zip[the OpenICF.Net Active Directory connector package].

You can also manage Active Directory through the bundled xref:chap-ldap.adoc#chap-ldap[LDAP connector] or implement custom operations using the xref:chap-powershell.adoc#chap-powershell[PowerShell Connector Toolkit]. See xref:chap-exchange.adoc#chap-exchange[Exchange Connector] for the separate Exchange integration.

[#ad-connector-config]
=== Configuring the Active Directory Connector

Install the xref:../integrators-guide/chap-resource-conf.adoc#net-connector-install[.NET Connector Server] and configure xref:../integrators-guide/chap-resource-conf.adoc#net-connector-openidm[OpenIDM's connection to it]. The server host needs Windows ADSI and network access to Active Directory. Match the remote server's protocol, port, TLS setting, and key in the OpenIDM configuration. The default TCP port for the legacy protocol is `8760`. The sample remote server configuration uses WebSocket on port `8759`.

[#d8013e16273]
.Setting Up the Active Directory Connector
====

. Stop the .NET Connector Server. Extract the Active Directory connector archive into the directory containing the server executable. Keep `ActiveDirectory.Connector.dll` and its dependency `Interop.ActiveDs.dll` alongside the executable, then start the server.
+
Give the server runtime account permissions to read the connector files and write to the configured log directory.

. Copy `samples/provisioners/provisioner.openicf-ad.json` to your OpenIDM project's `conf/` directory.

. Set `connectorHostRef` to the corresponding entry name in `conf/provisioner.openicf.connectorinfoprovider.json`. Match the `connectorRef` to the remote bundle shown by the xref:../integrators-guide/chap-resource-conf.adoc#connector-wiz-cli[connector configuration tools]. The OpenICF.Net 1.5.0 package uses these values.
+
[source,json]
----
{
  "connectorHostRef": "dotnet",
  "connectorName": "Org.IdentityConnectors.ActiveDirectory.ActiveDirectoryConnector",
  "bundleName": "ActiveDirectory.Connector",
  "bundleVersion": "1.5.0.0"
}
----

. Set the following values under `configurationProperties`.
+
[cols="2,1,4",options="header"]
|===
|Property |Default |Purpose
|`DirectoryAdminName` |`administrator` |Required bind identity with permissions for the configured operations. Enter a domain-qualified username such as `EXAMPLE\svc-openidm` as `"EXAMPLE\\svc-openidm"` in JSON.
|`DirectoryAdminPassword` |Unset |Required password for the bind identity.
|`DomainName` |Empty |Required AD domain name, for example `example.com`. Used to look up the schema and discover a server for synchronization.
|`Container` |Empty |Required default search base DN, for example `OU=Employees,DC=example,DC=com`. An OpenICF search can supply a different container. Writes use the object's DN.
|`ObjectClass` |`User` |AD object class for accounts. It must be nonempty.
|`LDAPHostName` |Empty |DNS name of the domain controller. An empty value lets ADSI discover a server. For provisioning with Global Catalog searches, choose a host that also serves writable LDAP for the target domain.
|`SearchChildDomains` |`false` |Set to `true` to search the Global Catalog under the selected base. The connector tries to read each live result over LDAP for attributes outside the catalog's partial attribute set.
|`SyncDomainController` |Unset |Domain controller used for liveSync when `SearchChildDomains` is `false`. An unset value triggers discovery.
|`SyncGlobalCatalogServer` |Unset |Global Catalog used for liveSync when `SearchChildDomains` is `true`. An unset value triggers discovery.
|`CreateHomeDirectory` |`true` |Also attempts to create a directory when it sets a valid UNC path in `homeDirectory`. Set to `false` to manage only the AD attribute.
|`SearchContext` |Value of `Container` |Exposed for legacy configurations. Set `Container` or the operation's container to change the search base in 1.5.0.0.
|===
+
Keep the liveSync server stable because the synchronization token tracks change sequence numbers from that server. See the link:https://github.com/OpenIdentityPlatform/OpenICF.Net/blob/1.5.0/dotnet-connector/ActiveDirectoryConnector/ActiveDirectoryConfiguration.cs[configuration source] for the connector property definitions.

. Test the provisioner, then query the sample's `account` object type. These commands assume your OpenIDM URL is `http://localhost:8080/openidm` and the sample name is `ActiveDirectory`. Set `OPENIDM_USER` and `OPENIDM_PASSWORD` to your OpenIDM credentials before running the examples.
+
[source,console]
----
$ curl \
  --header "X-OpenIDM-Username: $OPENIDM_USER" \
  --header "X-OpenIDM-Password: $OPENIDM_PASSWORD" \
  --request POST \
  "http://localhost:8080/openidm/system/ActiveDirectory?_action=test"

$ curl \
  --header "X-OpenIDM-Username: $OPENIDM_USER" \
  --header "X-OpenIDM-Password: $OPENIDM_PASSWORD" \
  "http://localhost:8080/openidm/system/ActiveDirectory/account?_queryFilter=true"
----
+
The connection test should return `"ok": true`. The query lists account records visible to the connector. The sample also exposes `Group` and `organizationalUnit` for search and provisioning. Authentication and liveSync are available for accounts.

[#ad-reconciliation]
=== Reconciling Active Directory Accounts

The following mapping imports AD accounts into the default `managed/user` resource. Use a test container whose accounts have values for `sAMAccountName`, `givenName`, `sn`, and `mail`, which supply the required managed user properties. Add this entry to the `mappings` array of your project's `conf/sync.json`.

[source,json]
----
{
  "name": "systemADAccounts_managedUser",
  "source": "system/ActiveDirectory/account",
  "target": "managed/user",
  "properties": [
    { "source": "sAMAccountName", "target": "userName" },
    { "source": "givenName", "target": "givenName" },
    { "source": "sn", "target": "sn" },
    { "source": "mail", "target": "mail" }
  ],
  "policies": [
    { "situation": "ABSENT", "action": "CREATE" },
    { "situation": "CONFIRMED", "action": "UPDATE" },
    { "situation": "SOURCE_MISSING", "action": "IGNORE" }
  ]
}
----

Run reconciliation and use the returned run ID to xref:../integrators-guide/chap-synchronization.adoc#recon-details[check its status]. Inspect the result in the Admin UI or query `managed/user` to verify the import. Review correlation and policies before sharing the target with other mappings. To process incremental account changes, configure xref:../integrators-guide/chap-synchronization.adoc#livesync-over-rest[LiveSync] for `system/ActiveDirectory/account`.

[source,console]
----
$ curl \
  --header "X-OpenIDM-Username: $OPENIDM_USER" \
  --header "X-OpenIDM-Password: $OPENIDM_PASSWORD" \
  --request POST \
  "http://localhost:8080/openidm/recon?_action=recon&mapping=systemADAccounts_managedUser"
----

[#ad-powershell]
=== Using PowerShell Scripts With the Active Directory Connector

This connector implements OpenICF `ScriptOnResource`. It runs a configured PowerShell or Shell action on the Windows connector server. Update `systemActions` in the OpenIDM provisioner to register the scripts you intend to call. For instance, the following action echoes a supplied argument.

[source,json]
----
{
  "systemActions": [
    {
      "scriptId": "echoLogin",
      "actions": [
        {
          "systemType": "Org[.]IdentityConnectors[.]ActiveDirectory[.]ActiveDirectoryConnector",
          "actionType": "PowerShell",
          "actionSource": "Write-Output $loginName"
        }
      ]
    }
  ]
}
----

Use `actionFile` in place of `actionSource` to load a script from the OpenIDM project's filesystem. OpenIDM reads the file and sends the script source to the connector server.

For a test project with a rule authorizing the `script` action on `system/ActiveDirectory`, call the registered action as follows. For a production endpoint, expose only the intended action through a xref:../integrators-guide/chap-scripting.adoc#custom-endpoints[custom endpoint] with authorization for that action.

[source,console]
----
$ curl \
  --header "X-OpenIDM-Username: $OPENIDM_USER" \
  --header "X-OpenIDM-Password: $OPENIDM_PASSWORD" \
  --request POST \
  "http://localhost:8080/openidm/system/ActiveDirectory?_action=script&scriptId=echoLogin&scriptExecuteMode=resource&loginName=example"
----
