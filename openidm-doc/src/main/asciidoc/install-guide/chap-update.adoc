[#chap-update]
== Updating OpenIDM

OpenIDM 7 distributions omit the maintenance and update service. Plan a new installation from the target ZIP or container image, with a tested configuration and repository migration. Review the link:https://github.com/OpenIdentityPlatform/OpenIDM/releases[release notes] for both the source and target and for each intervening release that affects your deployment.

[#update-process]
=== Plan the Upgrade

anchor:install-update-process[]
anchor:openidm-update-repos[]

Use a staging copy to establish the upgrade path for your exact OpenIDM versions, Java runtime, database, JDBC driver, and connectors. Confirm the required migration steps and downtime before scheduling the change. For changes from an older major version, budget for changes to Java, configuration, scripts, bundled connectors, and data formats.

. Download the target distribution and use its default configuration as the base. Compare the source defaults, your deployed configuration, and the target defaults. Carry over your custom settings and validate them against the target version. Review `conf/`, scripts, workflows, custom connectors, and UI extensions. Check for custom JVM options and for paths or roles that may have changed.
. Record which repository engine, workflow datasource, and schema versions are in use. Review the SQL updates shipped for the repository engine under `db/<engine>/scripts/updates/` and the release notes. These directories can contain scripts for older versions. Identify the changes required for your source schema with your database administrator and run them in staging first. Use the schema initialization scripts only on empty databases.
. Back up the project, installation, and any configuration stored in the repository. Include the keystore, truststore, encryption keys, secrets, and persistent data or volume contents. Back up the JDBC database consistently and test restoring it. Save connector versions and the service startup settings with the backup.
. Rehearse the deployment with a restored copy of the database and test credentials and connectors. Verify that the target can decrypt existing data, read and update managed objects, authenticate users, reconcile the expected records, and load the workflows and scheduled jobs you use.

[#maintenance-mode]
=== Take the Current Instance Out of Service

Plan a write-free maintenance window before taking the final backup and applying database changes. Stop accepting traffic and pause jobs or connectors that run outside OpenIDM. Shut down OpenIDM. For a cluster, drain and stop all nodes that share the repository before changing its schema, and keep the old nodes stopped while the target uses it.

[#upgrade-zip]
=== Deploy From the Binary Package

. Extract the target ZIP into a new directory and prepare the supported Java runtime. See xref:chap-install.adoc#install-openidm[To Install OpenIDM Services].
. Apply the project configuration and customizations validated in staging. Use the matching keystore and truststore from the backup where your data or credentials depend on their keys. Keep the original installation and its configuration available for rollback.
. Take the final consistent repository backup and apply the schema changes established in staging.
. Start the new instance and confirm that it reaches `ACTIVE_READY`. Test admin login, repository reads and writes, and the integrations exercised in the rehearsal. Restore scheduled work and client traffic after these checks.

[#upgrade-container]
=== Deploy From a Container Image

. Pin the target image tag. Rehearse the deployment with copies of its volumes and any external repository. Compare files in mounted configuration directories with the files shipped in the new image. For volumes and file ownership, see xref:../how-to/how-to-persist-openidm-configuration-data-between-restarts.adoc#how-to-persist-openidm-configuration-data-between-restarts[Persisting Container Data].
. Stop the current container after draining traffic and take the final backups. Apply the database changes and configuration changes verified in staging.
. Recreate the container with the target image and the prepared configuration and volumes. Wait for readiness and verify the same functions as for a ZIP deployment before restoring scheduled work and traffic.

[#upgrade-orientdb]
=== Plan a Migration From the Evaluation Repository

OpenIDM 7.1 switched from OrientDB 2.x to 3.x. Keep the original database and runtime together until you have verified how to migrate the data. For a production deployment, migrate to a JDBC repository. Rehearse your data migration and check the objects, relationships, configuration, and runtime state that it copies before cutover.

[#upgrade-rollback]
=== Roll Back a Failed Upgrade

Stop the target installation or container and keep traffic and scheduled work paused. Restore the original configuration, keys, and repository from the same pre-upgrade backup, then start the original version with that restored state. Before restoring traffic, verify readiness and the same key functions checked during rehearsal. If the upgraded system accepted writes, account for those changes before replacing its repository with the backup.
