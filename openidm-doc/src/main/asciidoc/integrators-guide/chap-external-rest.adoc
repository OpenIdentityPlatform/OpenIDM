[#chap-external-rest]
== Accessing External REST Services

Use the `external/rest` resource to make an outbound HTTP call from OpenIDM logic. For provisioning, synchronization, and reconciliation, use an OpenICF connector for the target service.

From an OpenIDM script, call the resource with a map of invocation parameters.

[source, javascript]
----
openidm.action("external/rest", "call", {
    "url": "http://localhost:8080/openidm/info/ping",
    "method": "GET",
    "headers": {
        "X-OpenIDM-Username": "anonymous",
        "X-OpenIDM-Password": "anonymous"
    }
});
----

The next example submits the same request through the REST API against a local evaluation instance. Export the evaluation server certificate as described in xref:chap-security.adoc#rest-over-https[Restrict REST Access to the HTTPS Port]. Set `OPENIDM_PASSWORD` in your shell and adjust the inner URL if you changed the local HTTP port or context path.

[source, console]
----
$ curl --fail-with-body --cacert self-signed.crt \
    --header "X-OpenIDM-Username: openidm-admin" \
    --header "X-OpenIDM-Password: $OPENIDM_PASSWORD" \
    --header "Content-Type: application/json" \
    --data '{
      "url": "http://localhost:8080/openidm/info/ping",
      "method": "GET",
      "headers": {
        "X-OpenIDM-Username": "anonymous",
        "X-OpenIDM-Password": "anonymous"
      }
    }' \
    "https://localhost:8443/openidm/external/rest?_action=call"
----

For a successful JSON response such as the ping result, OpenIDM returns the JSON directly by default. If the upstream response reaching the service has a non-2xx status, the action returns an error with the upstream status code and the message `HTTP request failed`.

[#invocation-parameters]
=== Invocation Parameters

Use these keys in the action body or script parameter map.

[cols="1,4",options="header"]
|===
|Parameter |Meaning
|`url` |Required target URL.
|`method` |Required HTTP method, for example `GET`, `POST`, or `PUT`.
|`headers` |Optional map of HTTP request headers.
|`body` |Optional request body as a string.
|`contentType` |Media type of the request body. A `Content-Type` entry in `headers` takes precedence. The default for a supplied body is `application/json; charset=utf-8`.
|`base64` |Set to `true` to decode a base64-encoded request `body` before sending it. Defaults to `false`.
|`forceWrap` |Set to `true` to include upstream headers and body in a JSON envelope even when the upstream response is JSON. Defaults to `false`.
|`authenticate` |Optional authentication configuration. For HTTP Basic authentication, use `{"type":"basic","user":"example","password":"example-password"}`. For a bearer token, use `{"type":"bearer","token":"example-token"}`.
|===

The `openidm.external.rest.tls.version` property in `conf/boot/boot.properties` selects the SSL context algorithm for outbound HTTPS. The service defaults to `TLSv1.2`.

[#non-json-responses]
=== Support for Non-JSON Responses

OpenIDM wraps responses with a non-JSON media type. It also wraps JSON responses when the action body contains `"forceWrap": true`. The envelope contains a `headers` object, with arrays of header values, and a `body` string. Text and XML use the response text. For a binary response, `body` contains base64-encoded data and the envelope includes `"base64": true`.

Set `"forceWrap": true` in the ping example to receive an envelope like this one. The exact upstream headers depend on the running instance.

[source, json]
----
{
  "headers": {
    "Content-Type": ["application/json;charset=UTF-8"]
  },
  "body": "{\"_id\":\"\",\"state\":\"ACTIVE_READY\",\"shortDesc\":\"OpenIDM ready\"}"
}
----
